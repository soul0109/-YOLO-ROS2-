## 3. 总体目标与 MVP 边界

### 3.1 最终目标

在 Gazebo 中启动一个带相机和激光雷达的差速巡检机器人，完成：

```text
启动仿真 → 建图/定位 → Nav2 多点巡检 → 相机检测异常
→ 异常地图定位 → 事件和截图归档 → Web 查看和下发任务
```

### 3.2 第一版 MVP

**边界以 [`巡检场景规格.md`](巡检场景规格.md)（v0.1）为准**，摘要如下：

- **场景：** 室内机房固定路线 — 充电/起点 → 3 个设备柜巡检点 → 终点；
- **机器人：** 400×300 mm 差速底盘；相机 0.12 m 水平前视；激光 0.22 m 360°；
- **判据：** 指示灯 / 面板显示 / 区域外观三类机器可判定目标（详见场景规格 §3）；
- **导航：** 到点 ≤0.20 m、朝向 ≤10°、停稳 1.0 s 内 |v|<0.02 m/s 且 |ω|<0.05 rad/s；
- **视觉：** 停车 1.0~1.5 m 处异常检出率 ≥90%（阶段 5 定基准，非 mAP）；
- **基础链路：** `/cmd_vel`、`/odom`、`/scan`、`/camera/image_raw` 正常（阶段 3 已验收）。

Web 和 LLM 属于第二阶段能力。LLM 即使暂时不做，也不影响项目主体成立。

## 4. 关于“建模最难”的判断

你的判断基本正确，但难点不是单纯画出一个漂亮机器人，而是以下模块必须同时一致：

| 模块 | 典型问题 | 解决策略 |
|---|---|---|
| 几何模型 | 尺寸、方向、比例错误 | 所有尺寸先用米，建立尺寸表 |
| 碰撞模型 | 机器人穿墙、卡住、抖动 | visual 和 collision 分离，collision 先用简单几何体 |
| 惯性参数 | 出生后翻滚、抽搐、漂移 | 先使用合理近似值，验证稳定后再精细化 |
| 关节与 TF | 轮子不转、坐标系断裂 | 固定 frame 命名和 TF 树 |
| Gazebo 插件 | `/cmd_vel` 无效、无里程计 | 插件逐个接入，先底盘再传感器 |
| 传感器 | 话题有数据但 frame 错 | 每个传感器单独检查 topic、frame_id 和频率 |
| 场景碰撞 | 地图与实际墙体不一致 | 场景模块化，先做小测试房间 |
| 导航参数 | 原地打转、过不去门 | footprint、轮距、膨胀半径与真实尺寸一致 |

所以解决方案不是“一次性把模型做好”，而是把模型拆成多个可验收版本。

## 5. 推荐的建模路线

### 5.1 机器人：先功能模型，再外观模型

推荐采用“自建最小差速底盘 + Gazebo 基本几何体”的路线：

1. `robot_v0`：底盘、两个驱动轮、一个万向轮，全部使用 box/cylinder；
2. `robot_v1`：加入激光雷达和相机，打通 TF 与传感器；
3. `robot_v2`：优化材质、外壳、相机支架和展示效果；
4. 最终只保留对导航和视觉有价值的外观细节。

这样做的优点是每一步都能运行，也便于理解 URDF、xacro、插件和 TF。

如果 `robot_v0` 连续调试超过两天仍不稳定，再临时使用 TurtleBot3 作为导航基线；但最终项目仍建议保留自己的机器人模型，避免作品变成“只会启动官方机器人”。

### 5.2 机器人坐标系约定

第一版固定使用：

```text
map → odom → base_footprint → base_link
                              ├→ laser_link
                              └→ camera_link
```

- `base_footprint`：二维导航平面；
- `base_link`：机器人主体中心；
- `laser_link`：雷达光心；
- `camera_link`：相机坐标系；
- 所有 frame 名称使用小写下划线，不随意改名；
- 轮距、轮半径、底盘长宽和传感器高度写入 xacro 参数。

### 5.3 地图：同时保留“调试地图”和“项目地图”

地图也不要一步到位：

- `test_room`：小房间或短走廊，只用于验证机器人、雷达、SLAM 和 Nav2；
- `factory_v1`：包含走廊、3 个房间、障碍物和巡检点，用于最终演示；
- `factory_map`：由 SLAM 实际建图并保存，用来证明系统不是手工摆拍；
- 必要时保留一份已知可用地图，专门用于隔离 Nav2 参数问题。

推荐的 `factory_v1` 初始规模：约 10m × 10m，2～3 个房间，走廊宽度至少 1.2m，门宽至少 1.0m，先不加入动态行人。

### 5.4 场景资产：先用原语，不依赖在线模型库

墙、地面、箱子、柱子等优先用 Gazebo/SDF 原语搭建。人员、灭火器等目标只在视觉阶段加入。

这样可以避免：模型下载失败、比例不一致、材质缺失、碰撞体缺失和许可证不清晰等问题。

## 6. 分阶段开发路线与验收闸门

### 阶段 2：ROS2 通信 demo

产出：`inspection_demos`、状态查询 service、Action server、参数 YAML、demo launch、TF 静态变换。

**`RobotStatus.srv` 初版字段（阶段 2 定稿，后续按需扩展）：**

```text
# 请求：空
---
string robot_id
string status          # idle | patrolling | error
float32 battery_percent
geometry_msgs/Pose pose
```

完成标准：topic、service、action、launch、参数、TF 均能用 ROS2 命令验证。

### 阶段 3：机器人模型与传感器

建议顺序：

1. URDF 能在 RViz 显示；
2. xacro 参数化；
3. Gazebo 能生成机器人；
4. `/cmd_vel` 能驱动机器人；
5. `/odom` 和 TF 正常；
6. 加入 `/scan`；
7. 加入 `/camera/image_raw`；
8. 用一个 launch 统一启动。

阶段闸门：机器人不会翻倒或穿模，能够移动，四个核心话题都有正确数据和 frame_id。

### 阶段 4：小场景与导航基线

**场景建模 = 巡检场景建模。** `test_room` 墙体与目标物高度按 [`巡检场景规格.md`](巡检场景规格.md) 执行（目标中心 **0.45 m**）。

建议顺序：

1. **4.0** 场景规格冻结（`巡检场景规格.md` v0.1）✅
2. **4.1** `test_room` 世界：通道 + 3 设备柜位 + 指示灯/面板占位；
3. 键盘遥控检查里程计和雷达；
4. **4.2a** rosbag2 录制 / 回放工作流（四话题 + TF，可离线复盘）；
5. **4.2b** 里程计漂移分析：Gazebo `libgazebo_ros_p3d.so` ground truth 对比 `/odom`，出漂移曲线；
6. SLAM 建图并保存地图；
7. AMCL 加载地图定位；
8. Nav2 单点 → 3 航点巡检路线。

**阶段闸门（场景驱动，非「建出图即过」）：**

| 项 | 指标（同场景规格 §5） |
|---|---|
| 地图质量 | 支撑巡检几何：通道、停车区、目标高度带可复现 |
| AMCL | 定位误差 **≤ 0.10 m** |
| Nav2 到点 | 位置 **≤ 0.20 m**、朝向 **≤ 10°**、停稳 1.0 s 内 \|v\|<0.02 m/s 且 \|ω\|<0.05 rad/s |
| 任务 | **3 航点**单圈**无人工干预** |

**可选项（不阻塞阶段 4 闸门）：**

- IMU + `robot_localization` EKF 融合（阶段 4 完成后评估）；
- CI 流水线（B 级，不急）。

### 阶段 5：YOLO ROS2 化

先验证以下链路，再追求模型精度：

```text
图像话题 → cv_bridge → YOLO（找目标） → ROI 颜色/亮度（状态判定） → DetectionArray → 标注图话题
```

先使用普通图片或 rosbag 验证节点，再将仿真相机接入。原生 Ultralytics 推理跑通后，再切换 ONNX Runtime。

**内部门槛（滚动计划 M1/M2）：**

| 门槛 | 含义 | 过线证据 |
|---|---|---|
| **5A** | 推理链路成立 | 固定权重、`model_path` 非空、框/置信度/stamp/耗时/标注图可复现 |
| **5B** | 巡检判据成立 | 场景规格 **v0.1.1 首切片**（灯+面板+漏液）独立测试集检出率 **≥ 90%**；ROI 可配置；UNKNOWN 有用例 |

5A 过 ≠ 5B 过。滚动切片与先不做清单见 [`作品集闭环滚动计划.md`](作品集闭环滚动计划.md)。

**阶段闸门（场景驱动）：**

- 在**实际巡检距离 1.0~1.5 m**、车头正对目标条件下，**首切片**综合检出率 **≥ 90%**（定基准数据集，**非 mAP**；口径见场景规格 §5.1）；
- 检测结果可通过 `ros2 topic echo` 查看，标注图能显示，回调不会因推理阻塞而不断积压。

### 阶段 6：检测定位与巡检任务

**MVP（先做）：站点级事件关联**

- Patrol / 到站停稳后触发拍照检测（**不**把 AMCL≤0.10 m 当硬阻塞触发条件；定位门禁单独记质量字段）；
- 事件关联 `mission_id` + `station_id`（A/B/C）+ 预定义站点位姿；
- 时间窗去重；任务结束输出 JSON + 截图目录；每站都有结果（含全 PASS）。

**后置（非 MVP）：** 检测框精确投影到 `map`（需可靠定位/深度或几何）；RGB-D 优先评估。

阶段闸门：3 航点无人干预完成；异常/结果事件含站点、时间、类别、状态、置信度、截图与 `model_version`。

### 阶段 7：Web 平台

按“后端先行、前端后做”的顺序。

**最小可演示切片（先做）：**

1. FastAPI 任务创建/状态 + 事件 CRUD/查询；
2. Vue：固定地图 A/B/C、任务状态、站点结果表、事件列表与截图；
3. 可选轻量 WebSocket 状态；原始相机全量转发 **暂缓**。

后置：轨迹回放、检测视频面板、复杂交互地图。

### 阶段 8：收尾与可选 LLM

完成 README、架构图、演示视频、一键启动/健康检查、演示脚本与全新环境复现。可选：少量 pytest / launch_testing 回归。LLM 只有在前面闭环稳定后才开始。

## 6.5 MVP 优先执行顺序（2026-11-08 起生效）

> **决策：** 用户已同意「MVP 优先、分步交付」。本顺序**明确取代**旧依赖——「先完成采集适配器 / 正式 Test 准备才能进入任务层」。  
> 此处**只记录顺序与验收边界**，不展开未来全部任务书。每项 **独立实施 → 审查 → 验收**。  
> 阶段 5–8 的产品闸门（检出率、站点事件、Web、复现）仍有效；达线路径改为经 MVP-R1…R7 切片推进。

### 6.5.1 切片顺序

| 切片 | 内容 | 验收边界（摘要） |
|---|---|---|
| **MVP-R1** | 固定 A 站真实任务 Action 入口，**只做导航** | `ExecuteInspection`（或等价）能下发并完成 A 站导航；不做检测/归档/Web |
| **MVP-R2** | 停稳确认、新相机帧、截图与元数据 | 到站停稳后取得新帧并落盘截图+元数据；不做在线 YOLO 判定 |
| **MVP-R3** | 同帧 YOLO+ROI 在线判定 | 对 R2 同帧做在线判定并输出站点结果；**非正式 Test 达线声明** |
| **MVP-R4** | SQLite 任务与站点结果归档 | Runtime **单写** SQLite；任务/站点结果可查询；不做 FastAPI/Vue |
| **MVP-R5** | FastAPI 任务接口与结果查询 | 同 VM 查任务/结果；**Web 不直接控制运动** |
| **MVP-R6** | Vue 单站最小操作与结果页面 | 单站发起/查看；不做全量视频流 |
| **MVP-R7** | 扩展固定 A/B/C 路线，多站闭环 | 固定三站无人干预闭环（导航已知限制如实保留） |
| **最终验证与交付** | 正式视觉 Test、复现入口、演示与限制说明 | 正式评估完成后方可宣称视觉达标；含演示脚本与已知限制 |

### 6.5.2 正式 Test 与采集支线

- 现有 **隔离与计分要求保持**（见数据集规范 / 采集清单专节；本回合不改协议正文）。
- **采集工具支线暂停**（含 C2A / C2A-R1 已实施待审成果）：**不删除**；暂停 ≠ 取消。
- **MVP-R3 通过后**恢复限定 pilot，再安排正式采集与冻结。
- 正式 Test 成绩 **不阻塞** MVP-R4–R7 软件开发。
- **最终视觉达标声明及交付验收前**必须完成正式评估。
- **禁止**把旧开发池升格为正式 Test；开发视觉成绩 ≠ 正式独立 Test。

### 6.5.3 架构纪律（保留 M0.2）

- 模块化单体；**一个** Mission Runtime；`ExecuteInspection.action` 为任务入口。
- 视觉 / 归档为进程内模块；**Runtime 单写 SQLite**。
- FastAPI 与 Runtime **同 VM**；Web **不直接控制运动**。

### 6.5.4 任务审查阻塞边界

**只阻塞当前问题：** 正常路径不通、结果失真、取消语义错误、数据错误、冻结基线被越权修改等。  
扩展性、通用恢复、低概率组合和非关键优化记**技术债**，不自动扩大当前任务。

## 9. 建模问题排查顺序

遇到机器人不动、抖动、翻滚或导航失败时，严格按下面顺序排查：

1. 是否生成了正确的模型；
2. visual 和 collision 是否位置一致；
3. inertial 是否存在且数值合理；
4. 轮子 joint 轴方向是否正确；
5. Gazebo 插件参数中的轮半径和轮距是否与模型一致；
6. `/odom` 是否随移动变化；
7. TF 是否存在且方向正确；
8. 雷达的 `frame_id` 是否正确；
9. footprint、膨胀半径和通道宽度是否匹配；
10. 最后才调 Nav2 控制器参数。

不要一上来修改十几个 Nav2 参数。先找出第一个错误的坐标系或物理参数。

### 12.4 可靠性、数据、视觉与AI边界

**可靠性**先做错误分类、统一异常停止/终态、启动对账与安全拒绝，再针对具体故障有限重试。导航响应未知不等于未执行；Action终态不等于物理零速。重启默认保留中断事实、不盲目续跑；旧Nav2状态未确认时不开放新任务。不自动重置initialpose、不无限重发目标、不承诺exactly-once。取消HTTP接口独立设计并复用Action停止确认。

**持久化**先保持现有schema；评审终态发布/释放与归档提交顺序、损坏payload处理、原子文件写入和失败证据保留策略。历史原始证据不覆写；如需纠错展示，标明派生结果及计算版本。未来设备模型为device_id→inspection_item_id→observation(mission/station/时间/判定/原因/证据/模型与规则版本)。先从objects JSON只读投影，业务需要后再单独批准schema迁移。人工确认/处置记录需另定写入所有权，不能默让API写Runtime归档。

**正式视觉**沿既有M2-5B合同：主距1.2m≥60图(ABC各≥20)，辅1.0/1.5m各≥5，≥3独立会话，主距UNKNOWN≥10/难例≥10；五字段(3灯+panel+leak)主报，漏检/处理失败计错。先登记候选完整权重SHA256、ROI内容哈希、依赖与推理参数，再限定pilot、独立采集/人工GT、来源与近重复审查、Test冻结、候选模型规则冻结与首次评估。禁止Test调参；未达标如实报告。候选登记不等于最终正式冻结；单站A清单不替代ABC合同；场景改动另授权，不降配额。C2A成果保留，现场可行性未证实前不得虚报通过。

**设备历史**先看观察次数、FAIL频次、UNKNOWN率与证据；不同版本分组，不把UNKNOWN计异常，不把一次PASS说成长久健康。报告优先可复用查询/打印，PDF后置。

**Agent**先文本只读状态/历史/证据问答，再增加受限任务下发与取消；业务API校验参数、权限、确认与幂等，记录请求ID/mission_id。语音ASR/TTS最后接输入输出，不绕过Runtime。具体本地/云端选型在文本流程与VM资源实测后再定。

### 14.4 设计原则与必须展开的细节

**A. 并发与所有权**

给出真实线程/回调组→共享状态→锁的映射、锁顺序及伪代码。优先一个权威Runtime状态锁保护owner/generation、busy、安全标志和ticket/context原子交接，是否复用现有runner/slot锁须依据调用图决定。避免简单给每函数各加一把锁；说明Runtime锁、Runner锁、Archive锁、bridge锁之间的顺序。

**B. 停止与未知响应**

**C. 终态、归档与错误路径**

设计候选终态与对外最终结果的区分。说明正常、用户取消、导航异常、采集/推理异常、payload损坏、站写失败、finalize失败、Action结果发送失败每个分支如何处理。SQLite不提供与文件、ROS通信的跨系统原子提交，不声称解决所有崩溃窗口。

**D. 启动对账与单实例**

优先保守启动、不自动续跑。分离启动屏障与任务执行状态。说明单实例锁作用范围（同DB/同机器人），仅DB进程锁不能防不同DB的两个Runtime控制同一机器人；不为解决本项目单机部署引入分布式租约。

### 15.1 当前调用 / 线程与状态写入图（证据）

**线程与回调**

| 来源 | 符号 | 共享写入 |
|---|---|---|

**Runner→State 真实调用链（修订前缺口）**

现状：`MissionRunner` 在 `with self._lock`（`threading.RLock`）内直接调用：

- `_still_owner()` → `state.is_owner`
- `_enter_canceling_feedback` / `start` 路径 → `state.set_phase`
- `_emit_terminal` → `state.try_publish_terminal`

因此原「持 runner 时不获取 state？」为错误问号；任意 `state_lock` 方案必须与这条链兼容，不能假设 Runner 从不嵌套访问 State。

**Window 锁类型**

`AcceptedGoalWindow._lock` 为 **`threading.Lock`（不可重入）**。外层已持同一把锁再调用 `consume_for_install` / `record_cancel_for_awaiting`（内部再次 `with self._lock`）会**自死锁**。

**已有保证（保留）**

- 单任务意图、`used_mission_ids` + seed、generation 校验、`terminal_published` 防双发意图。
- Runner：cancel 响应 ≠ 停止；需匹配目标 result 终态；超时 → `cancel_unconfirmed` + `mark_unsafe` + orphan。
- 迟到 send after unsafe：orphan cancel、不二次业务终态（方向已有）。
- Runtime 唯一写 SQLite；Reader `query_only`。
- 执行态 ⊥ 巡检态；V2-01 FAIL>UNKNOWN>PASS DONE。

**确定缺口（本修订对象）**

1. State 无锁；与 Runner 嵌套访问未定义；Window 普通 Lock 不可外持内调。
2. `resolve_cancel`：slot 未命中到 ticket 查询之间、以及 consume→install 之间存在取消丢失窗口。
3. `add_done_callback` 对已完成 future **可能同步执行回调**；挂回调≠“之后才跑”。
4. 无 handle ≠ 未执行；原故障矩阵“确认无 handle 可 release”错误。
5. `_publish_once(release)` / `clear_if_owner` 早于 `_finalize_archive`；`terminal_published` 语义混用候选与已发布。
6. HTTP 504 伪业务 FAILED；前端 `busy`/poll 仅认 `ACCEPTED`/`RUNNING`；`observation` 与执行态未分离。
7. unsafe 仅内存；无运动前持久化 refuse；flock 未按机器人身份固定。
8. 读盘失败空 `objects` 仍可 `ok=True`；表 D 曾写“删壳/标完成”——**作废**。

### 15.2 业务不变量（≤8）与四张表

**不变量（PROPOSED）**

1. 占用（active / control_unknown / archive_degraded）存在时拒绝新任务。
2. mission_id 不可复用（内存 ∪ 归档已见）。

#### 表 B — 锁与 I/O 边界（无问号）

**选定锁序（单一无环）**

1. **权威占用锁：`state_lock` = `threading.RLock`**，保护 owner/generation/busy/unsafe/archive_degraded/used ids/phase、以及 **ticket 与 slot 的逻辑内容**。
2. **`AcceptedGoalWindow` / `MissionActiveSlot`：实施时取消对外可重入的独立 `Lock` 用法**；改为仅提供在 **已持有 `state_lock`** 下调用的 `_unlocked_*` 私有方法。公共薄封装若保留，只获取 **一次** `state_lock`，内部转调 `_unlocked_*`，**禁止**再嵌套 Window/Slot 自锁。
3. **`MissionRunner._lock`（RLock）**：只保护 runner 局部（stop_mode、futures 句柄、orphan、deadline）。  
   **嵌套规则（固定）：允许 `runner_lock → state_lock`；禁止 `state_lock → runner_lock`。**  
   因而：goal/cancel/install/execute 权威路径 **只拿 `state_lock`**，需要 `request_cancel` 时 **先锁内记录 pending / 取出 runner 引用，释放 `state_lock` 后再** `runner.request_cancel()`。

4. **`MissionArchive._lock`**：仅在 **未持有 `state_lock`** 时做 SQL。
5. **`RosMissionBridge._lock`**：独立观察层；**不是**安全屏障。

**`add_done_callback` 纪律**

- 注册 callback **必须在释放 `runner_lock`/`state_lock` 之后**（或证明回调体不再获取与注册路径相反的锁）。
- 因已完成 future 可能 **同步** 进入回调：回调开头按上述锁序获取锁；不得假设“挂上后锁已释放才跑”。

**模式：** 锁内验证/认领/记录取消意图 → 锁外 I/O 与 `request_cancel` / 挂 callback → 返回后锁内核对 generation 再提交。

3. **Commit occupancy**：再持 `state_lock`：若仍为本 generation 的 finalizing，则 `terminal_committed=candidate`（或失败则 archive_degraded+占用），**仅在非 control_unknown 且归档成功（或已批的失败终态已落库）时 release**。

  generation = begin_unlocked(mission_id)         # reserved

### 16.2 必须补正的五组问题

1. **锁方案必须可执行，不能保留问号。** §15表B写“持runner时不获取state？”而当前runner在持RLock时调用_still_owner/set_phase/finish等state操作。必须列出实际调用链，选定单一无环锁序或消除嵌套；不得只写“先快照再runner”而漏掉回调内state访问。T1的with state_lock在assert后已退出，consume/install没有被权威锁整体保护；且现有Window._lock是普通threading.Lock，外层持它再调用consume_for_install会自锁。明确外层权威锁与Window/Slot内部锁是否保留、是否用locked私有方法，禁止混用。future.add_done_callback可能对已完成future同步执行回调，挂回调不等于没有外部调用；放到锁外或证明可重入无反向调用。取消记录在锁内、request_cancel在锁外，完整覆盖查slot失败到查ticket的间隙与consume到install的间隙。

2. **未知导航事件必须明确列入首个相关实施片。** §15.6“确认无handle则可release”错误：没有handle不能证明请求未执行。只有显式reject、发送前确定本地失败且有可靠证据未发出，或匹配目标已确认终态，才可证明本次导航无需继续占用；其余同步/future异常均归控制未知并有界stop/unsafe。具体区分local preflight和send调用异常，别猜底层异常表示未发送。当前B1没列runner修补却承诺“未知控制不放行”，范围与退出条件不一致，必须重排。unsafe终态发出后晚到结果只清理/补证据，默认不自动解除安全屏障、不二次发布业务终态；人工解除另定受控合同。

3. **持久化屏障需要写前纪律与机器人级锁。** 在unsafe终态时才写schema_meta不能覆盖“可能发送后、标记前崩溃”。必须比较在任何可能运动之前持久化refuse/active，停止已确认且归档完成后才clear的写前方案，与每次启动都需受控确认方案。明确持久化写失败时禁止后续导航；clear失败仍保持拒绝。标记按DB保存不能覆盖切换DB，需同时说明同一机器人使用不同库时启动为何仍拒绝未知状态。flock需固定机器人级路径(如用户runtime目录+固定robot_id)，不跟INSPECTION_ARCHIVE_DB变化；由Runtime进程持有FD直到退出，不能只在可绕过的启动脚本加锁。仅同用户同主机范围，不宣称分布式锁。锁目录、权限、身份、释放/崩溃语义和人工确认绑定本次启动/实例写清；进程锁可得仅证明无同锁进程，不证明Nav2空闲。

4. **保全历史，定义可达的终态与失败收口。** §15表D“人工标完成或删壳”不接受。禁止删除RUNNING壳、伪造COMPLETED、人工直接SQL回填；允许未来Runtime唯一写者在确认停止后按已批准合同追加/更新为明确INTERRUPTED，并保留原原因/时间/已完成站；如需新工具/字段须声明待批。终态候选、认领finalizing、commit成功、Action发送、释放之间给出精确线性化点；terminal_published不能既表示候选已认领又表示最终已发布。finalize失败保持archive_degraded且返回明确失败是推荐方向，但不能把未成功写入DB说成持久化成功。异常发生在每个阶段有有界出口，已持久化终态在Action回复丢失后仍可查询。payload首选验证内存InspectResult.payload，但文件保存失败不能绕过，空/缺关键字段作为执行失败，不以UNKNOWN继续掩盖技术错误。

5. **PENDING必须是观察状态，端到端兼容要明确。** 推荐独立observation_status=PENDING/UNKNOWN与业务execution status区分，避免把新增PENDING混入业务终态枚举。列出schemas、GET、POST504、bridge、前端busy/poll的最小兼容影响；现前端只按ACCEPTED/RUNNING轮询，新增status=PENDING会停止轮询，不能说只改后端即兼容。API result future异常也不能伪造机器人FAILED或释放本地未知占用。无live只有DB RUNNING时展示“持久化进行中记录/当前执行未知”，不宣称当前确在运行/空闲；终态archive优先，部分站结果仍可查。明确迟到accept回调一次挂result监听、超时与接收竞态及API重启后的观察限制。

### 2.2 YOLO vs ROI（职责冻结）

```text
YOLO：定位区域（indicator_light / panel / inspection_region）
ROI ：颜色/亮度/面积规则 → PASS | FAIL | UNKNOWN
事件 ：mission + station 上下文 → 结构化记录 + 截图
```

- 灯的红/绿/黄/灭 **不是** 四个检测类，是同一类框 + ROI。
- **UNKNOWN ≠ FAIL**；漏检不得默认为 PASS。

### 2.3 检测触发 vs AMCL 门禁（实现约束）

| 条件 | 用途 |
|---|---|
| 到站 + 新鲜odom确认停稳（任务语义） | 可触发新帧采集；GT仅仿真诊断，不作视觉判定或运行控制 |
| AMCL ≤0.10 m | **单独质量字段**；不得作为「永远不检测」的硬阻塞 |

否则视觉写好了也会被未过的定位门禁卡死。
