## 3. 总体目标与 MVP 边界

### 3.1 最终目标

在 Gazebo 中启动一个带相机和激光雷达的差速巡检机器人，完成：

```text
启动仿真 → 建图/定位 → Nav2 多点巡检 → 相机检测异常
→ 异常地图定位 → 事件和截图归档 → Web 查看和下发任务
```

### 3.2 第一版 MVP

**边界以 [`巡检场景规格.md`](巡检场景规格.md)（v0.1）为准**，摘要如下：

- **场景：** 室内机房固定路线 — 充电/起点 → 3 个设备柜巡检点 → 终点；
- **机器人：** 400×300 mm 差速底盘；相机 0.12 m 水平前视；激光 0.22 m 360°；
- **判据：** 指示灯 / 面板显示 / 区域外观三类机器可判定目标（详见场景规格 §3）；
- **导航：** 到点 ≤0.20 m、朝向 ≤10°、停稳 1.0 s 内 |v|<0.02 m/s 且 |ω|<0.05 rad/s；
- **视觉：** 停车 1.0~1.5 m 处异常检出率 ≥90%（阶段 5 定基准，非 mAP）；
- **基础链路：** `/cmd_vel`、`/odom`、`/scan`、`/camera/image_raw` 正常（阶段 3 已验收）。

Web 和 LLM 属于第二阶段能力。LLM 即使暂时不做，也不影响项目主体成立。

## 4. 关于“建模最难”的判断

你的判断基本正确，但难点不是单纯画出一个漂亮机器人，而是以下模块必须同时一致：

| 模块 | 典型问题 | 解决策略 |
|---|---|---|
| 几何模型 | 尺寸、方向、比例错误 | 所有尺寸先用米，建立尺寸表 |
| 碰撞模型 | 机器人穿墙、卡住、抖动 | visual 和 collision 分离，collision 先用简单几何体 |
| 惯性参数 | 出生后翻滚、抽搐、漂移 | 先使用合理近似值，验证稳定后再精细化 |
| 关节与 TF | 轮子不转、坐标系断裂 | 固定 frame 命名和 TF 树 |
| Gazebo 插件 | `/cmd_vel` 无效、无里程计 | 插件逐个接入，先底盘再传感器 |
| 传感器 | 话题有数据但 frame 错 | 每个传感器单独检查 topic、frame_id 和频率 |
| 场景碰撞 | 地图与实际墙体不一致 | 场景模块化，先做小测试房间 |
| 导航参数 | 原地打转、过不去门 | footprint、轮距、膨胀半径与真实尺寸一致 |

所以解决方案不是“一次性把模型做好”，而是把模型拆成多个可验收版本。

## 5. 推荐的建模路线

### 5.1 机器人：先功能模型，再外观模型

推荐采用“自建最小差速底盘 + Gazebo 基本几何体”的路线：

1. `robot_v0`：底盘、两个驱动轮、一个万向轮，全部使用 box/cylinder；
2. `robot_v1`：加入激光雷达和相机，打通 TF 与传感器；
3. `robot_v2`：优化材质、外壳、相机支架和展示效果；
4. 最终只保留对导航和视觉有价值的外观细节。

这样做的优点是每一步都能运行，也便于理解 URDF、xacro、插件和 TF。

如果 `robot_v0` 连续调试超过两天仍不稳定，再临时使用 TurtleBot3 作为导航基线；但最终项目仍建议保留自己的机器人模型，避免作品变成“只会启动官方机器人”。

### 5.2 机器人坐标系约定

第一版固定使用：

```text
map → odom → base_footprint → base_link
                              ├→ laser_link
                              └→ camera_link
```

- `base_footprint`：二维导航平面；
- `base_link`：机器人主体中心；
- `laser_link`：雷达光心；
- `camera_link`：相机坐标系；
- 所有 frame 名称使用小写下划线，不随意改名；
- 轮距、轮半径、底盘长宽和传感器高度写入 xacro 参数。

### 5.3 地图：同时保留“调试地图”和“项目地图”

地图也不要一步到位：

- `test_room`：小房间或短走廊，只用于验证机器人、雷达、SLAM 和 Nav2；
- `factory_v1`：包含走廊、3 个房间、障碍物和巡检点，用于最终演示；
- `factory_map`：由 SLAM 实际建图并保存，用来证明系统不是手工摆拍；
- 必要时保留一份已知可用地图，专门用于隔离 Nav2 参数问题。

推荐的 `factory_v1` 初始规模：约 10m × 10m，2～3 个房间，走廊宽度至少 1.2m，门宽至少 1.0m，先不加入动态行人。

### 5.4 场景资产：先用原语，不依赖在线模型库

墙、地面、箱子、柱子等优先用 Gazebo/SDF 原语搭建。人员、灭火器等目标只在视觉阶段加入。

这样可以避免：模型下载失败、比例不一致、材质缺失、碰撞体缺失和许可证不清晰等问题。

## 6. 分阶段开发路线与验收闸门

### 阶段 2：ROS2 通信 demo

产出：`inspection_demos`、状态查询 service、Action server、参数 YAML、demo launch、TF 静态变换。

**`RobotStatus.srv` 初版字段（阶段 2 定稿，后续按需扩展）：**

```text
# 请求：空
---
string robot_id
string status          # idle | patrolling | error
float32 battery_percent
geometry_msgs/Pose pose
```

完成标准：topic、service、action、launch、参数、TF 均能用 ROS2 命令验证。

### 阶段 3：机器人模型与传感器

建议顺序：

1. URDF 能在 RViz 显示；
2. xacro 参数化；
3. Gazebo 能生成机器人；
4. `/cmd_vel` 能驱动机器人；
5. `/odom` 和 TF 正常；
6. 加入 `/scan`；
7. 加入 `/camera/image_raw`；
8. 用一个 launch 统一启动。

阶段闸门：机器人不会翻倒或穿模，能够移动，四个核心话题都有正确数据和 frame_id。

### 阶段 4：小场景与导航基线

**场景建模 = 巡检场景建模。** `test_room` 墙体与目标物高度按 [`巡检场景规格.md`](巡检场景规格.md) 执行（目标中心 **0.45 m**）。

建议顺序：

1. **4.0** 场景规格冻结（`巡检场景规格.md` v0.1）✅
2. **4.1** `test_room` 世界：通道 + 3 设备柜位 + 指示灯/面板占位；
3. 键盘遥控检查里程计和雷达；
4. **4.2a** rosbag2 录制 / 回放工作流（四话题 + TF，可离线复盘）；
5. **4.2b** 里程计漂移分析：Gazebo `libgazebo_ros_p3d.so` ground truth 对比 `/odom`，出漂移曲线；
6. SLAM 建图并保存地图；
7. AMCL 加载地图定位；
8. Nav2 单点 → 3 航点巡检路线。

**阶段闸门（场景驱动，非「建出图即过」）：**

| 项 | 指标（同场景规格 §5） |
|---|---|
| 地图质量 | 支撑巡检几何：通道、停车区、目标高度带可复现 |
| AMCL | 定位误差 **≤ 0.10 m** |
| Nav2 到点 | 位置 **≤ 0.20 m**、朝向 **≤ 10°**、停稳 1.0 s 内 \|v\|<0.02 m/s 且 \|ω\|<0.05 rad/s |
| 任务 | **3 航点**单圈**无人工干预** |

**可选项（不阻塞阶段 4 闸门）：**

- IMU + `robot_localization` EKF 融合（阶段 4 完成后评估）；
- CI 流水线（B 级，不急）。

### 阶段 5：YOLO ROS2 化

先验证以下链路，再追求模型精度：

```text
图像话题 → cv_bridge → YOLO（找目标） → ROI 颜色/亮度（状态判定） → DetectionArray → 标注图话题
```

先使用普通图片或 rosbag 验证节点，再将仿真相机接入。原生 Ultralytics 推理跑通后，再切换 ONNX Runtime。

**阶段闸门（场景驱动）：**

- 在**实际巡检距离 1.0~1.5 m**、车头正对目标条件下，三类判据（指示灯 / 面板 / 外观）综合检出率 **≥ 90%**（阶段 5 定基准数据集，**非 mAP**）；
- 检测结果可通过 `ros2 topic echo` 查看，标注图能显示，回调不会因推理阻塞而不断积压。

### 阶段 6：检测定位与巡检任务

- RGB-D 优先于纯单目；
- 检测框中心或底边点转相机坐标；
- 通过 TF 转到 `map`；
- 异常事件按时间和空间去重；
- Patrol Action 调用 Nav2；
- 到达航点后触发拍照/检测；
- 任务结束生成 JSON 和截图目录。

阶段闸门：3 个航点无人干预完成，异常事件有地图位置、时间、类别、置信度和截图。

### 阶段 7：Web 平台

按“后端先行、前端后做”的顺序：

1. FastAPI 事件 CRUD；
2. 任务下发接口；
3. 状态和事件 WebSocket；
4. 地图/轨迹面板；
5. 视频和检测面板；
6. 报告查询和回放。

图像使用低分辨率、低帧率专用话题，避免把原始相机流直接通过 WebSocket 全量转发。

### 阶段 8：收尾与可选 LLM

完成 README、架构图、演示视频、一键启动和全新环境复现。LLM 只有在前面闭环稳定后才开始。

## 9. 建模问题排查顺序

遇到机器人不动、抖动、翻滚或导航失败时，严格按下面顺序排查：

1. 是否生成了正确的模型；
2. visual 和 collision 是否位置一致；
3. inertial 是否存在且数值合理；
4. 轮子 joint 轴方向是否正确；
5. Gazebo 插件参数中的轮半径和轮距是否与模型一致；
6. `/odom` 是否随移动变化；
7. TF 是否存在且方向正确；
8. 雷达的 `frame_id` 是否正确；
9. footprint、膨胀半径和通道宽度是否匹配；
10. 最后才调 Nav2 控制器参数。

不要一上来修改十几个 Nav2 参数。先找出第一个错误的坐标系或物理参数。

## 10. 完成定义

本项目的最低交付线是：

- 一条命令启动仿真；
- 机器人模型稳定；
- 相机和雷达话题正常；
- 地图和 TF 正确；
- Nav2 能完成多点移动；
- YOLO 能输出结构化检测结果；
- 巡检任务能生成异常报告；
- README 能指导他人复现。

视觉外观、复杂动态障碍物、LLM 和真实硬件都属于加分项，不应阻塞最低交付线。
