## 二、架构与锁：保留必要原则，停止堆机制

当前仍是模块化单体：Web→FastAPI/ROS ActionClient→单Mission Runtime→Nav2/视觉→Runtime单写SQLite；API/CLI只读巡检归档，Web不直接控制/cmd_vel。

| 机制 | 技术判断 | 本阶段决定 |
|---|---|---|
| 进程内任务互斥/owner generation | Runtime使用多线程回调；两次任务、取消与结果回调可能交错。单任务业务不等于单线程 | 必须保留并保证原子预留、旧回调不能影响新任务 |
| Nav2停止确认/未知状态占用 | 超时或无响应不能证明目标未执行；直接发新目标可能叠加 | 必须保留；Action终态不等于物理急停 |
| SQLite事务与Runtime单写 | 保护结果一致性与边界 | 保留现有Reader只读和唯一写者，不为简化引入多写者 |
| 机器人级flock | 防同机重复Runtime；在单实例受控启动下是部署防呆，不是ROS强制要求 | 可以保留现有标准flock，但不声称证明Nav2空闲或跨主机安全；不扩分布式锁 |
| safety JSON/持久屏障 | 覆盖崩溃后内存状态丢失和换DB；与同库RUNNING壳部分重复 | 已接入且存在未验证恢复缺陷，不能静默旁路；本阶段只实现可理解、可用的最小人工恢复，不造自动续跑 |
| token + 自定义文件IPC + 离线CLI | 为跨进程确认与唯一写者而增加；不是ROS2任务必须，也不是同用户安全权限边界 | 明显偏复杂；允许下一批在保留防误操作、单写和可控停机前提下精简或替换；不得无方案删除/双写 |

**简化约束**：不因仿真直接释放未知导航、删除单任务互斥、清空历史/标记、放宽正常owner校验。V2-02现有代码不是已验收基线；先保护工作区和对照已有MVP证据，再根据主流程定位最小修复。可选方案如以固定数据库RUNNING壳代替独立标记，必须说明换库、DB损坏和进程崩溃时的限制与如何防止误放行；不能假设两者等价。无真实故障或产品需求，不追加通用状态机、重试、token/IPC协议增强。

## 三、后续推进：按完整产品批次

| 顺序 | 目标 | 交付标准 |
|---|---|---|
| 1 | 基线保护与恢复现有可运行产品 | 盘点并保存未跟踪源码/依赖/权重来源；当前源码能从干净启动进入可操作状态，正常任务/历史浏览不因新增机制永久拒绝；已知缺陷如实记录 |
| 2 | 可视化运行控制台（下一完整Cursor批次） | 在现有Web增加只读地图、机器人位姿/朝向、任务目标与状态、规划路径/会话轨迹，以及低帧率原始相机；过期/不可用不伪造实时；Web仍走API、不直控运动 |
| 3 | 独立视觉Test质量支线 | 沿现有合同登记候选权重/规则哈希、隔离来源、人工GT、按既定ABC与距离配额采集并报告；实采和场景改变另按操作授权，不以开发池充Test |
| 4 | 作品集交付 | 一次合并验证冷启动、三站、代表性失败/取消；整理可复现说明、视频、架构图、真实指标与限制，然后集中准备面试 |
| 可选 | 设备历史、有限恢复、文本Agent/语音 | 主流程和证据成熟后按实际价值选择，不作为控制台前置 |

上述1/2建议作为一个连续产品批次：先不破坏现有运行栈地保护和定位，再实现监控；在确认操作窗口前，可完成源码/离线测试/前端构建。**只有真实冷启动、重启服务和任务实跑需要用户明确窗口**。不要因为恢复增强未完善就无限期阻塞Web开发，也不要宣称新版已经稳定运行。

- 复用 `apply_vision_scene_gt.py` / 现有瞬移采图链路；检测框可用 1.2m 固定窗作候选标注，状态 GT 来自场景种子+人工约定，**禁止**模型写 GT。
