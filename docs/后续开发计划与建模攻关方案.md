## 二、架构与锁：保留必要原则，停止堆机制

当前仍是模块化单体：Web→FastAPI/ROS ActionClient→单Mission Runtime→Nav2/视觉→Runtime单写SQLite；API/CLI只读巡检归档，Web不直接控制/cmd_vel。

| 机制 | 技术判断 | 本阶段决定 |
|---|---|---|
| 进程内任务互斥/owner generation | Runtime使用多线程回调；两次任务、取消与结果回调可能交错。单任务业务不等于单线程 | 必须保留并保证原子预留、旧回调不能影响新任务 |
| Nav2停止确认/未知状态占用 | 超时或无响应不能证明目标未执行；直接发新目标可能叠加 | 必须保留；Action终态不等于物理急停 |
| SQLite事务与Runtime单写 | 保护结果一致性与边界 | 保留现有Reader只读和唯一写者，不为简化引入多写者 |
| 机器人级flock | 防同机重复Runtime；在单实例受控启动下是部署防呆，不是ROS强制要求 | 可以保留现有标准flock，但不声称证明Nav2空闲或跨主机安全；不扩分布式锁 |
| safety JSON/持久屏障 | 覆盖崩溃后内存状态丢失和换DB；与同库RUNNING壳部分重复 | 已接入且存在未验证恢复缺陷，不能静默旁路；本阶段只实现可理解、可用的最小人工恢复，不造自动续跑 |
| token + 自定义文件IPC + 离线CLI | 为跨进程确认与唯一写者而增加；不是ROS2任务必须，也不是同用户安全权限边界 | 明显偏复杂；允许下一批在保留防误操作、单写和可控停机前提下精简或替换；不得无方案删除/双写 |

**简化约束**：不因仿真直接释放未知导航、删除单任务互斥、清空历史/标记、放宽正常owner校验。V2-02现有代码不是已验收基线；先保护工作区和对照已有MVP证据，再根据主流程定位最小修复。可选方案如以固定数据库RUNNING壳代替独立标记，必须说明换库、DB损坏和进程崩溃时的限制与如何防止误放行；不能假设两者等价。无真实故障或产品需求，不追加通用状态机、重试、token/IPC协议增强。

## 三、后续推进：按完整产品批次

| 顺序 | 目标 | 交付标准 |
|---|---|---|
| 1 | 基线保护与恢复现有可运行产品 | 盘点并保存未跟踪源码/依赖/权重来源；当前源码能从干净启动进入可操作状态，正常任务/历史浏览不因新增机制永久拒绝；已知缺陷如实记录 |
| 2 | 可视化运行控制台（下一完整Cursor批次） | 在现有Web增加只读地图、机器人位姿/朝向、任务目标与状态、规划路径/会话轨迹，以及低帧率原始相机；过期/不可用不伪造实时；Web仍走API、不直控运动 |
| 3 | 独立视觉Test质量支线 | 沿现有合同登记候选权重/规则哈希、隔离来源、人工GT、按既定ABC与距离配额采集并报告；实采和场景改变另按操作授权，不以开发池充Test |
| 4 | 作品集交付 | 一次合并验证冷启动、三站、代表性失败/取消；整理可复现说明、视频、架构图、真实指标与限制，然后集中准备面试 |
| 可选 | 设备历史、有限恢复、文本Agent/语音 | 主流程和证据成熟后按实际价值选择，不作为控制台前置 |

上述1/2建议作为一个连续产品批次：先不破坏现有运行栈地保护和定位，再实现监控；在确认操作窗口前，可完成源码/离线测试/前端构建。**只有真实冷启动、重启服务和任务实跑需要用户明确窗口**。不要因为恢复增强未完善就无限期阻塞Web开发，也不要宣称新版已经稳定运行。

### 目标和工作范围

1. 先核实VM仓库/branch/HEAD/status与运行服务，保存本批修改前的精确基线（包括未跟踪文件）。盘点当前代码、权重/依赖和启动入口。无需新建总计划、无需重复全仓审计；绝不clean/reset/stash、覆盖现有文件或改历史bags。
2. 沿用现有Runtime/Action/导航/归档，定位当前代码冷启动及人工恢复的实际障碍。优先解决首次启动缺标记、旧实例标记人工恢复、恢复期间新任务并发等会让主流程不可用或错误的具体问题；可以对复杂恢复实现做最小精简，先在报告给出修改理由和保留/删除的边界，保持任务互斥、停止确认、单写与历史完整。不要为了完成这批重写整个Runtime、换状态机、重做R1–R7或继续扩展恢复协议。
3. 在现有FastAPI桥和Vue页面上完成一个可用控制台：OccupancyGrid静态地图、map坐标机器人位姿与方向、A/B/C、当前目标、规划路径与有界会话轨迹；只读遥测附数据时间与过期状态；相机采用有限帧率JPEG/MJPEG或等价轻量方案。历史截图仍是正式巡检证据，实时画面不可冒充到站检测；无数据、断线、仿真暂停清楚表示未知/过期，不显示假在线。
4. 地图按OccupancyGrid origin/resolution/行列和Canvas纵轴转换；TF位姿不能重复应用现有world→map标定。路径frame不匹配需正确转换或明确不可显示，绝不通过改冻结地图/航点让画面对齐。
5. 保持HTTP→ExecuteInspection的唯一入口，A/B ToPose、B→C ThroughPoses一次提交、Runtime单写、COMPLETED与巡检状态分离；旧V2-01结果语义与历史记录不回填。已运行服务未经用户确认不重启、不发ROS目标，不操作真实证据库或默认安全目录。

### 技术选择与避免过度建设

- 复用现有FastAPI进程中的ROS桥接生命周期；HTTP轮询或只读WebSocket按实际频率择简，缓存有界、慢客户端丢旧图，不阻塞巡检推理与回调。Canvas优先；不引入rosbridge/WebRTC/大型渲染框架，除非用现有环境实测明确必要。
- 电池暂无真实来源则不展示或明确标模拟；AMCL静止更新有运动门限，不能仅凭无新消息宣称定位丢失。GT只做仿真诊断，不作为地图定位或视觉判定输入。
- 正式视频传输、实时YOLO、健康全家桶、异常工单、数据库迁移、设备趋势、Agent/语音均不在本批。

### 验证与验收

- 开发阶段用已有测试、必要fake/临时目录验证任务互斥、停止未知不放行、恢复认领不接受新任务、标记/归档失败不假成功；增加少量地图变换、数据过期及前端基本交互测试。只测实际改动，不按测试数量评估，不反复跑通过的同一组，不拿单测冒充实跑。
- 前端构建；产出一套可复制启动/恢复命令。无需本批重新训练模型、正式Test、导航十轮、全仓回归。
- 若未获服务操作窗口：完成代码和离线验证后交一次REVIEW，真实冷启动/三站/取消列待验证；不得说整个产品已运行通过。获窗口后另以一次有目的的产品验证检查控制台与巡检联动；失败时优先修主流程，限制和证据如实记录。
- 返回真实baseline与每个修改文件的before/after（包括未跟踪源码）、架构变化/为何需要、测试与构建输出、截图或运行证据（若已获得窗口）、已知限制、恢复说明；不自标最终交付完成。一个完整批次结束后由主架构统一审查，不为每个helper/缺陷开文档和审批。
- 仅主流程不通、结果失真、运动控制状态不明却放行、归档错误、越权冻结改动阻断推进；其他可解释限制记债务。任何重大架构/接口/数据库契约变更若不能在既有原则内解决，列出原因请用户决策。
