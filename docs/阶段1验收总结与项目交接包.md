## 4. 关键决策（不要轻易推翻）

1. **Ubuntu 22.04 + Humble + Gazebo Classic 11**（24.04/Jazzy 不作主路径）  
2. **协议先行**：节点只认 `inspection_interfaces`  
3. 业务节点 **Python**；C++ 用于读官方栈  
4. YOLO → ONNX；回调与推理解耦（线程+队列）  
5. Web：FastAPI + rosbridge + Vue3  
6. LLM **只做任务层** JSON，不进实时控制回路  
7. 第 1–10 周 **纯仿真**，不买硬件

## 5. 已知坑

- `cd -YOLO-ROS2-` 会被 bash 当成选项 → 使用 `~/inspection-robot`  
- 新终端必须 `source /opt/ros/humble/setup.bash`；编过 ws 后再 `source ros2_ws/install/setup.bash`  
- turtlesim 窗口与键盘是**两个节点**，只开 `teleop` 不会有海龟窗口  
- Windows 与 VM 是两套环境：改文档可在 Windows Cursor；**跑 ROS 必须在 VM**

## 6. 后续执行建议（独立判断，供对照）

> 计划 10 周仍有效，但执行上建议「闸门制」，避免平行开火导致半成品堆叠。

### 6.1 接下来 7 天（阶段 2）——只做通信肌肉记忆

| 顺序 | 产出 | 完成标准 |
|---|---|---|
| 1 | `inspection_demos`：pub/sub 巡检日志 | `ros2 topic echo` 可见；两节点对得上 |
| 2 | service：查假机器人状态 | `ros2 service call` 有结构化返回 |
| 3 | action：模拟巡检进度反馈 | 能看到 feedback / result |
| 4 | launch + YAML 参数 | 一条命令起上述节点 |
| 5 | TF2 静态 `base_link→camera_link` | `view_frames` 出 PDF/图 |

**不要**在阶段 2 就开始写 YOLO / Nav2 / Web。欠的是 ROS 通信与 launch 纪律，不是算法。

### 6.2 阶段节奏风险（相对原计划）

| 阶段 | 判断 |
|---|---|
| 3 仿真 | 可按计划；优先「能 `/cmd_vel` + `/scan` + `/camera/image_raw`」再美化场景 |
| 4 视觉 | 用户已有 YOLO 基础，重点在 **cv_bridge + 自定义 msg + 推理线程**，先 COCO person 跑通 |
| 5 Nav2 | **最可能延期**；单独留 buffer，调参记笔记进 `docs/` |
| 6 任务状态机 | 依赖 Nav2 Action 稳定；异常去重（时空）必做 |
| 7 Web | 用户主场，可与 6 部分并行，但图像话题必须降分辨率专用话题 |
| 8 LLM | 可砍可留；简历有 1–7 已够用，8 是加分 |
