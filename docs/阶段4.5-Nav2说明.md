## 0. 这步在项目里干什么？你要巩固什么？

```text
/map + AMCL TF  +  /scan
        ↓
Nav2（全局规划 NavFn + 局部 DWB + 双 costmap）
        ↓
/cmd_vel → cmd_vel_timeout → /cmd_vel_gazebo → diff_drive
```

| 你要会 | 说明 |
|---|---|
| **launch 分层** | `amcl_test_room`（Gazebo+map+AMCL）+ `navigation_launch`（**不用** `bringup_launch`，避免重复起 map/AMCL） |
| **footprint vs radius** | 写了 `footprint` 多边形就**不能**再写 `robot_radius` |
| **双 costmap 坐标系** | `global_costmap.global_frame=map`；`local_costmap.global_frame=odom` |
| **验收尺子** | 到位/航向用 `/ground_truth`（world）；停稳用 `/odom` twist；**不是** AMCL pose |
| **坐标只转一次** | world→map 仅在发 goal / initialpose 时用 `coords.py`，之后不再手算 |

### 和前后步骤的关系

```text
4.4 AMCL     →  map→odom TF（本步输入）
4.5a Nav2    →  骨架 + 走廊冒烟 + 闸门脚本（本步）
4.5          →  A/B/C 单点验收 → 三航点巡环（4.5b）
```

**真机要不要 Nav2？** 要。仿真 ground truth 只用于**自动验收**；真机靠 AMCL + 激光，闸门改人工抽检或 UWB 对标。

## 4. 操作步骤

### 4.1 启动 Nav2 栈

**终端 A：**

```bash
source /opt/ros/humble/setup.bash
source ~/inspection-robot/ros2_ws/install/setup.bash
ros2 launch navigation_config nav2_test_room.launch.py
```

等待 Gazebo + RViz 起来。另开终端：

```bash
source /opt/ros/humble/setup.bash
source ~/inspection-robot/ros2_ws/install/setup.bash
python3 ~/inspection-robot/scripts/publish_amcl_initial_pose.py
```

**顺序要点：**

1. 等 `/scan` 有数据后再发 initialpose（脚本会等 AMCL 订阅匹配）。  
2. **未发 initialpose** 时 `map` 帧不存在 → `planner_server` 激活卡住 → `bt_navigator` 一直 `inactive`。  
3. **车已移动后不要**把 initialpose 重发回充电垫——会撕裂 AMCL 与真值。

### 4.2 冒烟判定（人工，非正式闸门）

```bash
ros2 node list | grep -E 'controller|planner|bt_navigator|behavior|smoother|velocity|cmd_vel_timeout'
ros2 lifecycle get /bt_navigator          # active [3]
ros2 lifecycle get /controller_server     # active [3]
```

RViz（Fixed Frame = **map**）：

- Global / Local Costmap 出现；三门膨胀**不封死**（`inflation_radius=0.35` 首轮不调）。  
- Nav2 Goal 手点走廊空旷处 → 有红色 `/plan`，车能动。

走廊冒烟 map 点（= world(2.0,3.0) − origin）：

```text
map = (2.013, 2.948, yaw=0)
```

### 4.3 正式单点验收（`navigate_to_pose_gate.py`）

**终端 B**（A 保持 launch 运行，且已发 initialpose）：

```bash
source /opt/ros/humble/setup.bash
source ~/inspection-robot/ros2_ws/install/setup.bash
python3 ~/inspection-robot/scripts/navigate_to_pose_gate.py \
  --world-x 2.0 --world-y 3.0 --yaw 0
```

**闸门默认**（同 [`巡检场景规格.md`](巡检场景规格.md) §5）：

| 指标 | 阈值 | 数据源 |
|---|---|---|
| 位置 | ≤ **0.20 m** | `/ground_truth` vs world 目标 |
| 航向 | ≤ **10°** | 同上，yaw 归一化到 [-π,π] |
| 停稳 | 到位后 **1.0 s 内**沉降（\|v\|<0.02、\|ω\|<0.05），沉降后无再超标 | `/odom` twist，SUCCEEDED 后起 1 s 窗 |

**停稳语义（对齐《巡检场景规格》§5）：** 判的是**沉降时间**，不是「SUCCEEDED 瞬间全样本达标」。`navigate_to_pose_gate.py` 在窗内找首次达标时刻 `settle`，要求 `settle ≤ 1.0 s` 且之后无再次超标。

**输出示例：**

```text
Goal (x, y, yaw): (2.0, 3.0, 0.0)
Position Error: 0.170 m  PASS
Yaw Error:      5.5 deg  PASS
Stopped (settle 0.10 s): PASS
[stopped] samples=92  max|v|=0.0537 m/s  ...
[diag] AMCL vs GT at goal: 0.085 m
FINAL: PASS
```

`[diag]` 行区分**控制器/到点误差** vs **定位偏差**（AMCL map 位姿 vs GT 投影）。

## 5. 关键参数（`nav2_test_room.yaml`，首轮冻结）

| 类别 | 值 | 解决什么 |
|---|---|---|
| `robot_base_frame` | `base_footprint` | 与 diff_drive / AMCL 一致 |
| footprint | 0.40×0.30 中心对称多边形 | 车身碰撞包络；**无** `robot_radius` |
| DWB `max_vel_x` | 0.15 m/s | 慢速减 AMCL 动态漂移 |
| `xy_goal_tolerance` / `yaw_goal_tolerance` | **0.10 m** / 0.10 rad | 2026-08-31 3.0 收紧（原 0.15）；3.1 走廊 0.091 m、A 0.042 m、B 0.016 m、C 0.081 m |
| `velocity_smoother` | max_x=0.20, `OPEN_LOOP` | 与 DWB 限速一致，防默认隐性变量 |
| 双 costmap `inflation_radius` | 0.35 | 三门 1.1 m 可用窗口约 0.8 m |
| `cost_scaling_factor` | 5.0 | 膨胀衰减 |
| obstacle `scan` `min_range` | 0.30 m | 对齐 robot_v0 激光 |
| **progress_checker** `required_movement_radius` | **0.25** | 4.5b：原 0.5 在 0.15 m/s 门口易误触发 recovery |
| AMCL `alpha1–5`（`amcl_test_room.yaml`） | **0.05** | 4.5b 受控解冻：原 0.2 相对 T3 odom 噪声过高 |

**调参纪律：** 过不了门先查 costmap / footprint / obstacle 层；**禁止**同时动多组参数。4.5b 已按阶梯单点改过 progress_checker 与 AMCL alpha。

## 8. 学习问答

### 为什么不用 `bringup_launch`？

`bringup_launch` 会再起一套 map_server + AMCL，与 4.4 已验证的 `amcl_test_room` 重复，且易参数冲突。本项只 Include `navigation_launch.py`。

### 冒烟 recovery 是什么？

2026-08-31 走廊 NavigateToPose（spawn→走廊，~22 s）日志：

| 项 | 内容 |
|---|---|
| 触发 | `controller_server: Failed to make progress` |
| recovery | BT 默认 **Clear local costmap**（非 Spin/BackUp） |
| 位置 | 导航约 **18 s** 处（map 约从 (0.95,2.96) 向 (2.01,2.95) 中途） |
| 结果 | 清图 → 重规划 → ~4 s 后到点 SUCCEEDED |

### Stopped 1s 曾 FAIL、3.0c 怎么修的？

**现象（3.0b）：** SUCCEEDED 后 1 s 窗内 `max|v|≈0.054`，但仅窗口头 ~100 ms 超标，之后全程 <0.02。

**根因：** 旧闸门要求窗内**每个样本**达标；规格 §5 要的是**沉降时间** ≤1 s。

**3.0c 修复：** `navigate_to_pose_gate.py` 找首次 `|v|<0.02` 且 `|ω|<0.05` 的时刻 `settle`，PASS = `settle≤1.0 s` 且之后无再超标。输出 `Stopped (settle X.XX s): PASS/FAIL`。

**3.1 观察：** A/B/C 多为 `settle 0.00 s`（SUCCEEDED 瞬间 odom 已低于阈值，RotateToGoal 效应），非 flake。

**验收纪律：** 同航点**连续两次**同命令 FINAL PASS。

### `pkill -f gzserver` 误杀自己？

命令行含 `gzserver` 子串会被匹配。清场用 PID 列表或 `killall gzserver`（谨慎）。

### 4.5b 连续巡环为何挂、如何修好？

**根因（`bags/patrol_diag` 仪器复现，改参前一轮）：**

1. 门口慢行 → progress_checker（原 radius=0.5 / 10 s）易触发 recovery（本轮日志可无字面 `Failed to make progress`，但 clear→**Spin/BackUp** 时间线吻合）  
2. Spin/BackUp 风暴 → `/particle_cloud` rms≈2.4 m、AMCL cov 暴涨；首 Spin 时 |AMCL−GT|≈1.5 m  
3. AMCL 落入静态 OCCUPIED → `compute_path` / `follow_path` 死局（并出现 `Robot is out of bounds of the costmap`）  

**对照：** 3.1 分次闸门 ×2 的第二次多为「已在目标点」；**真链式直到 4.5b 才测到**。

**修复阶梯（每步一处）：**

| 步 | 改动 | 结果 |
|---|---|---|
| 2.1 | `required_movement_radius` 0.5→**0.25** | 走廊 PASS，无 Spin/BackUp |
| 2.2 | AMCL alpha1–5 0.2→**0.05** | 4.4 静止 max=**0.074 m**；走廊 PASS |
| 2.3/2.4 | 去 Spin·BackUp BT / 站点 initialpose | 未启用 |

**验收：** A→C→B FINAL PASS（recoveries 全 0）；规格 A→B→C FINAL PASS（C 1 次重试后过，recoveries=2）。
