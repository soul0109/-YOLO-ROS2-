## 0. 全局图：三种通信各管一件事

ROS2 节点之间只靠三种"对话方式"沟通，选型的判断标准只有一个——**任务的时长和方向**：

| 方式 | 模式 | 适合 | 本项目实例 |
|---|---|---|---|
| **Topic** | 持续广播，多对多，发者不知谁在听 | 传感器流、状态流、日志流 | `/scan` `/odom` `/camera/image_raw` |
| **Service** | 一问一答，同步，问完等答 | 即时查询、配置、触发 | `/get_robot_status` |
| **Action** | 目标→进度→结果，长任务，可取消 | 导航、巡检、任何秒级以上任务 | `/patrol_task`、`/navigate_to_pose` |

一张记忆图：

```text
Topic   = 广播电台：随时开机随时听，不听也不影响电台
Service = 打电话：你问我答，答完挂断（等不到回复就超时）
Action  = 点外卖：下单(goal) → 骑手位置实时推送(feedback) → 送达(result)，可中途退单(cancel)
```

**判据实例化**：机器人位姿每秒 100 次变化 → Topic；"现在电量多少"问一次
答一次 → Service；"巡一圈"要跑几分钟还要报进度 → Action。
把 `/navigate_to_pose` 归类 Action 而不是 Service，你就懂了 4.5 验收脚本
为什么是 Action Client。

**ROS2 与 ROS1 的一个底层区别**（面试常问）：ROS1 有中心 Master（roscore），
Master 挂了全网瘫痪；ROS2 去中心化，节点通过 **DDS 自动发现**彼此——
这才有阶段 4"随便先起谁都能连上"的体验（代价是 QoS 要自己配对，第 1 课讲）。

## 第 1 课：Topic + 节点骨架 + 参数

**教材：`log_publisher.py` / `log_subscriber.py` / `config/demos.yaml`**

### 1.1 节点骨架：每个节点都长一个样

```python
def main(args=None) -> None:
    rclpy.init(args=args)          # ① 初始化 rclpy 库（一次）
    node = LogPublisher()          # ② 构造节点（继承 rclpy.node.Node）
    try:
        rclpy.spin(node)           # ③ 进入事件循环：处理定时器/订阅回调
    except KeyboardInterrupt:      # ④ Ctrl-C 优雅退出
        ...
    finally:
        node.destroy_node()        # ⑤ 释放资源
        rclpy.shutdown()
```

**spin 是理解 ROS2 编程的钥匙**：你的代码从不"主动循环"，而是注册一堆
回调（定时器到点、消息到达），spin 负责监听并调用它们。整个项目所有节点
（阶段 4 的 gate 脚本、patrol 节点）都是这个骨架的变体——区别只是把
`spin` 换成 `spin_once` 循环以控制退出时机（见阶段 4 第 3 课）。

### 1.2 Publisher：队列深度 10 是什么

```python
self._publisher = self.create_publisher(String, '/inspection/log', 10)
```

第三个参数 `10` 是 **QoS 的 history depth**：发送/接收缓存里最多留最近
10 条，满了丢最旧的。它是最朴素的 QoS——阶段 4 你已经见过完整版
（BEST_EFFORT 传感器流 vs RELIABLE+TRANSIENT_LOCAL 低频关键消息），
那时再回头看这行，它就是 QoS 的冰山一角。

### 1.3 参数：declare → 读 → yaml 覆盖

```python
self.declare_parameter('log_interval_sec', 2.0)     # 声明+默认值
self._interval = float(self.get_parameter('log_interval_sec').value)  # 读取
```

```yaml
# config/demos.yaml —— launch 按节点名对号入座
log_publisher:
  ros__parameters:
    log_interval_sec: 2.0
    robot_id: "robot_01"
```

三段式纪律：**代码里 declare 给默认值 → yaml 里写覆盖值 → launch 注入**。
这样节点单独 `ros2 run` 也能跑（吃默认值），进 launch 才吃配置。
阶段 4 的 `nav2_test_room.yaml` 全文件都是这个机制的展开。

**一个真坑**：节点必须先 `declare_parameter` 才能接受外部参数——外部塞了
未声明的参数会报 `ParameterAlreadyDeclaredException` 或被忽略。
4.4 时 `publish_amcl_initial_pose` 的 use_sim_time 问题就是这个家族的。

### 1.4 订阅回调的铁律

```python
def _on_log_received(self, msg: String) -> None:
    self.get_logger().info(f'[订阅收到] {msg.data}')
```

代码注释里那句话值得背下来：**回调里不要做耗时操作**。spin 是单线程事件
循环，一个回调卡住，所有其他回调（包括定时器）全部排队等它。阶段 2 只打印
一行没事；**阶段 5 的 YOLO 推理一次几十毫秒，图像 30 Hz 进来必然积压**
——所以阶段 5 要么用独立线程池、要么降低处理频率，这个决定现在就要有预期。

## 第 2 课：Service + Action + 自定义接口设计

**教材：`robot_status_server.py` / `patrol_action_server.py` / `inspection_interfaces/*`**

### 2.1 接口文件：`---` 是一切的分界线

```text
# RobotStatus.srv
# 请求为空            ← 上半：Request（客户端填）
---
string robot_id       ← 下半：Response（服务端填）
string status         # idle | patrolling | error
float32 battery_percent
geometry_msgs/Pose pose
```

```text
# PatrolTask.action
geometry_msgs/PoseStamped[] waypoints   ← Goal（下单内容）
bool snapshot_on_arrive
string task_label
---
bool success                            ← Result（结局）
int32 visited_count
int32 anomaly_count
string report_path
string message
---
int32 current_index                     ← Feedback（途中实时推送）
int32 total_waypoints
string phase          # navigating | snapshot | anomaly_hold | idle
float32 progress      # 0.0 ~ 1.0
string current_label
```

记法：**srv 一刀切两半（请求/响应），action 两刀切三段（目标/结果/进度）**。
`.msg` 则没有分隔线，就是一包字段。接口文件由 `rosidl` 在编译期生成
C/Python 代码——所以 `inspection_interfaces` 是 CMake 包不是 setuptools 包，
且必须先于使用者编译。

### 2.2 Service 端：填 response 而不是 return 数据

```python
self.create_service(RobotStatus, '/get_robot_status', self._handle_request)

def _handle_request(self, request, response):
    _ = request                                  # 请求为空，显式表示"故意不用"
    response.robot_id = self._robot_id
    response.pose.orientation = Quaternion(x=0.0, y=0.0, z=0.0, w=1.0)  # 无旋转 = w=1
    return response
```

两个细节：① 空请求用 `_ = request` 显式标注，这是"我知道它是空的"的
自文档写法；② **单位四元数表示"没有旋转"是 (0,0,0,1) 不是 (0,0,0,0)**——
w=1 才是恒等旋转。全项目所有地方（coords.py、URDF）都遵守这个约定。

### 2.3 Action 端：三个回调各司其职

```python
ActionServer(self, PatrolTask, '/patrol_task',
    self._execute_callback,                    # 主执行体
    goal_callback=self._goal_callback,         # 收到目标：接还是拒？
    cancel_callback=self._cancel_callback)     # 收到取消：准还是不准？
```

- **goal_callback 是门卫**：可以在排队前拒绝非法目标（航点数为空、越界）。
- **cancel_callback 是态度**：ACCEPT 只表示"允许取消"，真正的取消动作在
  执行体里完成。
- **execute_callback 是主戏**，看它的取消处理结构：

```python
for index, waypoint in enumerate(waypoints):
    if goal_handle.is_cancel_requested:    # 每个航点循环开头都检查
        goal_handle.canceled()             # 标记结局为 CANCELED（不是 succeed！）
        result.success = False
        return result                      # 提前返回，后面的航点不走了
    goal_handle.publish_feedback(feedback) # 途中持续推送进度
    ...
goal_handle.succeed()                      # 全部完成才标记 SUCCEEDED
```

**结局三态由服务端显式声明**：`succeed()` / `canceled()` / `abort()`——
客户端在 `_on_result` 里收到的 status 就是这里定的。对照阶段 4 gate 脚本的
`_on_result`：`status != SUCCEEDED` 就 FAIL，一条链完全对上。

**Feedback 的设计质量**看 `phase` 字段：`navigating | snapshot | anomaly_hold |
idle`——它把阶段 6"到点拍照检测"的流程**提前写进了接口**。这是接口先行
的价值：客户端（未来 Web 前端）今天就能按这四种状态写 UI。

### 2.4 前向设计故事：第一天就定义了阶段 5/6 的接口

`inspection_interfaces` 在项目第一周就定稿了 4 个接口，对照它们的最终用途：

| 接口 | 定义于 | 实际启用 | 埋的伏笔 |
|---|---|---|---|
| `RobotStatus.srv` | 阶段 2 | 阶段 7 Web 状态查询 | 字段与手册 §阶段 2 定稿一致，未改过 |
| `PatrolTask.action` | 阶段 2 | 阶段 6 任务层 | phase 枚举含 snapshot/anomaly_hold；4.5b 的 patrol 节点在底层调 NavigateToPose，**PatrolTask 到阶段 6 包在它外面** |
| `Detection.msg` | 阶段 2 | **阶段 5 立刻用** | `xyxy` 像素框 + `confidence` + `track_id`（给目标跟踪留位） |
| `AnomalyEvent.msg` | 阶段 2 | 阶段 6 | `map_pose`（检测→TF→地图，阶段 4 的坐标课直接用）、`image_path`（截图存档）、`status: open/acknowledged/closed`（事件生命周期，Web 端确认/关闭异常） |

**这条故事线的面试价值**：接口在"消费者出现之前"设计，字段全是提前想好
的伏笔（track_id 给跟踪、map_pose 给定位联动、status 给 Web 状态机），
后续阶段只换实现不换协议——这是系统集成项目区别于"教程堆代码"的关键。

注意 `Detection` 的 `header` 里是 `frame_id=camera_link` 的像素框——
**从像素坐标到 map_pose 的那一步（阶段 6）正是阶段 4 学的 TF 变换**，
课程之间是咬合的。

## 第 3 课：Launch + 参数注入 + TF 入门

**教材：`demos.launch.py` / `static_tf_broadcaster.py`**

### 3.1 Launch：一键拉起一个系统

```python
Node(package='inspection_demos', executable='log_publisher',
     name='log_publisher', parameters=[config_file], output='screen')
```

四个关键件的分工：`executable` 指向 setup.py 注册的入口；`name` 决定节点名
（**它同时是 yaml 里找参数段的钥匙**）；`parameters=[yaml路径]` 注入配置；
`output='screen'` 把日志打到终端。**yaml 的顶层键 = 节点名**，对不上号的
段落静默不生效——"参数怎么没加载"九成是名字没对上。

### 3.2 TF：一棵坐标树，两种广播器

TF 的世界观：全系统维护**一棵坐标系树**，任何 frame 都能沿树变换到任何
其他 frame。树的边（变换）只有两种：

```python
StaticTransformBroadcaster(self)   # 静态边：装好后永远不变（相机支架、雷达位置）
TransformBroadcaster(self)         # 动态边：每帧都变（机器人在动）
```

- **静态边只发一次**：`StaticTransformBroadcaster` 是 latched 的——新节点
  加入了也能收到这条"过去发布"的变换（类似 QoS TRANSIENT_LOCAL，第 1 课
  的伏笔在这里闭环）。
- 动态边（odom→base_footprint）阶段 3 由 diff_drive 插件发布，
  map→odom 阶段 4 由 AMCL 发布——**阶段 4 五课复习里的 TF 链，就是
  静态边+两种动态边拼出来的完整树**：

```text
map ──动态(AMCL)── odom ──动态(diff_drive)── base_footprint
    └─静态(robot_state_publisher/URDF)─ base_link ─┬─ laser_link
                                                    └─ camera_link
```

### 3.3 这段 demo TF 是"占位"，真身阶段 3 才登场

demo 里 `base_link→camera_link` 用的是占位值 (0.10, 0, 0.30)，而真车 URDF
（`robot_v0.urdf.xacro:286`）是 `camera_offset_x=0.215, camera_offset_z=0.02`
（base_link 之上 0.215 m 前、0.02 m 上；base_link 离地 0.10 m → 相机离地
0.12 m，与场景规格一致）。**这不矛盾，是接口先行的又一次体现**：阶段 2
先用可参数化的静态广播器讲清"TF 怎么发"，阶段 3 真车模型由
`robot_state_publisher` 从 URDF 自动发布整棵树，demo 节点退役。

URDF 里还埋着一颗阶段 5 的种子——`camera_optical_frame`：

```xml
<joint name="camera_optical_joint" type="fixed">
  <parent link="camera_link"/>
  <child link="camera_optical_frame"/>
  <origin xyz="0 0 0" rpy="${-pi/2} 0 ${-pi/2}"/>   <!-- Z 前 X 右 Y 下 -->
</joint>
```

注释原话："ROS 光学系：Z 前、X 右、Y 下（阶段 5 YOLO/投影用）"。它存在
的原因：机械系（camera_link，X 前）和**光学系**（图像像素的行列方向）约定
不同，检测框的像素坐标要投影成 3D 方向必须先换到光学系——阶段 6 的
"检测框 → map_pose" 第一步就是这条 (−90°, 0, −90°) 的静态边。第一周的
URDF 又一次提前把后路铺好了。

### 3.4 yaw→四元数：同一把刀出现在三处

```python
transform.transform.rotation.z = math.sin(half_yaw)
transform.transform.rotation.w = math.cos(half_yaw)
```

`half_yaw = yaw/2` 这个"半角"细节，和 `scripts/coords.py` 的
`yaw_to_quat`、阶段 4 patrol 节点里的 goal 构造**是同一个公式**。四元数
避免欧拉角万向锁、插值平滑，代价是不直观——所以项目纪律是**凡转角度都
收敛到 coords.py 一个实现**（第 4.5 课讲过的"禁止第三次手算"）。

## 附录 A：术语表

| 术语 | 一句话解释 |
|---|---|
| rclpy | ROS2 的 Python 客户端库；init/spin/shutdown 三段式 |
| spin | 事件循环：监听定时器与消息到达并调用回调；回调阻塞=全部阻塞 |
| Node | 最小运行单元，有名字、参数、发布器/订阅器/服务/动作 |
| Topic / Pub / Sub | 广播频道 / 电台 / 收音机；多对多、发者不知听者 |
| Service / srv | 一问一答；`.srv` 用 `---` 分请求/响应两半 |
| Action / .action | 长任务三件套 goal/result/feedback；`---` 两刀切三段 |
| goal_callback / cancel_callback | ActionServer 的门卫与取消态度 |
| succeed()/canceled()/abort() | 服务端显式声明的三种结局 |
| QoS depth | 缓存最近 N 条、满则丢旧（KEEP_LAST） |
| BEST_EFFORT / RELIABLE | 允许丢帧保低延迟 / 保证必达（阶段 4 图像流 vs amcl_pose） |
| TRANSIENT_LOCAL | 晚加入的订阅者也能收到"过去"发布的消息 |
| DDS 自动发现 | ROS2 无中心 Master，节点间自动互相找到（对比 ROS1 roscore） |
| declare_parameter | 参数必须先声明才能被外部覆盖；yaml 顶层键=节点名 |
| launch / Node() | 一键拉起多节点；name 是 yaml 参数段的钥匙 |
| TF / TF 树 | 全系统坐标系树，任意 frame 沿树互变 |
| StaticTransformBroadcaster | 只发一次、latched 的坐标边（安装位） |
| robot_state_publisher | 从 URDF 自动解析并发布整棵模型 TF 树（阶段 3） |
| 四元数 (x,y,z,w) | 旋转表示；恒等=(0,0,0,1)；yaw 转 z/w 用半角公式 |
| rosidl | 接口文件→C/Python 代码的编译期生成器（接口包用 CMake） |
| 单位四元数陷阱 | "无旋转"是 (0,0,0,1) 不是全 0 |

## 附录 B：参考答案

**第 1 课**

1. 查电量是"问一次答一次"→ Service；持续上报是"流"→ Topic。判据是
   **交互的方向性和时长**：一次性同步查询用 Service，持续异步数据流用
   Topic。若 UI 每 0.5 s 刷一次电量，也可以让节点以 Topic 持续发布、
   UI 订阅——比 0.5 s 一次 Service 调用更自然。
2. 外部参数注入时报 `ParameterAlreadyDeclaredException`（rclpy 默认
   allow_undeclared=False）——表现为节点起不来，而非静默忽略。这就是
   为什么"参数没生效"要先查 declare，再查 yaml 键名。
3. 回调在单线程 spin 里执行：推理几十 ms × 图像 30 Hz > 处理能力 →
   订阅队列积压、消息越收越旧、其他回调（定时器/控制）被饿死。
   现象是"图像延迟越来越大、机器人控制变卡"。对策在阶段 5：独立线程/
   限频/丢旧帧（QoS BEST_EFFORT depth=1）。

**第 2 课**

1. Feedback 无法并入 Result：Result 只在任务结束时发一次，而进度的价值
   正在"途中"。用 Topic 另发进度可以工作（自定义进度 Topic），但会失去
   Action 的生命周期绑定——客户端取消后 Topic 进度还在发，多个并发的
   goal 的进度还会串台。Feedback 挂在 goal_handle 上，天然随 goal 生死。
2. `canceled()` 把 goal_handle 标记为 CANCELED 终态，客户端收到的
   status 是 CANCELED；不调直接 return，ActionServer 收不到合法终态，
   客户端可能一直等 result 或收到异常状态，服务端状态机也残留"执行中"。
3. 接口一旦有消费者（哪怕只是编译依赖），再改就是破坏性变更——所有
   使用方重新适配、已录的 bag 失效、git 历史断层。字段先占位（哪怕
   阶段 6 才填真值），消费者按最终契约开发，全程零迁移。

**第 3 课**

1. 吃不到。yaml 按"顶层键=节点名"匹配，键名对不上号 → 该段落整个静默
   不加载（无报错）。节点用 declare 的默认值照常启动——**静默失效**
   正是它难排查的原因，验证手段是 `ros2 param list` / `ros2 param get`。
2. StaticTransformBroadcaster 内部即 TRANSIENT_LOCAL 语义：发布过的
   变换对"迟到的订阅者"保持可得。和 amcl_pose 用 RELIABLE+TRANSIENT_LOCAL
   是同一个思想——关键的低频消息必须让晚来的人拿得到。
3. 两个发布者对同一条边发不同值 → TF 树里同父子对出现冲突边，
   lookupTransform 结果取决于时间戳，表现为"偶发跳变"级别的灵异问题。
   正确做法：模型相关的边只由 robot_state_publisher 发（单一事实源），
   demo 节点在真车上线后退役。**一条边只允许一个发布者**是 TF 纪律。
