## 0. 全局图：一个 URDF 文件 + 一个 Gazebo 扩展文件

阶段 3 的全部代码只有两个 xacro 文件，分工严格：

| 文件 | 管什么 | 关键内容 |
|---|---|---|
| `robot_v0.urdf.xacro` | **机器人长什么样、什么形状、多重** | link/joint、visual/collision/inertial、传感器安装位 |
| `robot_v0.gazebo.xacro` | **在 Gazebo 里怎么感知和驱动** | 材质/摩擦、diff_drive/ray/camera/p3d 四个插件 |

坐标系树（全项目 freeze 的框架约定）：

```text
base_footprint（地面投影点，导航用，空 link）
  └── base_link（车身中心，离地 0.10 m）
        ├── left_wheel_link  ┐ continuous 关节，绕 Y 轴
        ├── right_wheel_link ┘
        ├── caster_link（车头万向轮，fixed，三点支撑的另一足）
        ├── laser_link（车顶，扫描面离地 0.22 m）
        └── camera_link（前保险杠，光心离地 0.12 m）
              └── camera_optical_frame（光学系，阶段 5 用）
```

**读 xacro 的心法**：每个 `<xacro:property>` 都是一个"设计决定的数值化"。
后面每课都会拆几个：为什么是 0.28、为什么 0.30、0.22 怎么拼出来的。

## 第 1 课：URDF——形状、惯性、关节

### 1.1 link 三件套：长得像 / 撞得到 / 转得对

每个实体 link 都由三块组成，用途互不可替代：

```xml
<visual>    <!-- RViz/Gazebo 里"长什么样"：颜色、外观细节 -->
<collision> <!-- 物理引擎"撞到什么形状"：通常比 visual 简化 -->
<inertial>  <!-- 质量 + 转动惯量：决定动力学行为（翻不翻、飞不飞） -->
```

三个项目里的真实案例：

- **胎纹只放 visual**（`wheel_tread_pattern` 宏，轮缘 8 条小棱）：转起来
  肉眼可见像真轮子；collision 仍是光滑圆柱——外观不影响物理。
- **激光雷达只放 visual、不放 collision**（第 3 课详解，防射线打自己）。
- **inertial 是硬需求不是装饰**：Gazebo 里没有惯性或惯性不合理 →
  机器人翻倒、乱飞、穿透。三个现成宏按几何公式算：
  `box: Ixx = m(y²+z²)/12`、`cylinder: Iyy = mr²/2`（绕轴）、
  `sphere: I = 0.4mr²`（2/5 mr²）。面试常问"转动惯量怎么来的"——
  就是这几个标准公式。

### 1.2 base_footprint：一个"什么都没有"的 link，为什么存在

```xml
<link name="base_footprint"/>   <!-- 空：无 visual/collision/inertial -->

<joint name="base_joint" type="fixed">
  <parent link="base_footprint"/>
  <child link="base_link"/>
  <origin xyz="0 0 ${base_z}" rpy="0 0 0"/>   <!-- base_z = 轮半径+底盘半高 = 0.10 -->
</joint>
```

它是**"车在地面上的投影点"**——导航的二维世界只需要 (x, y, yaw)，不需要
知道车顶多高。把导航原点钉在地面而不是车身中心，好处：

1. costmap/footprint 的几何计算全在 z=0 平面，干净；
2. 车身改高改矮（base_height 调参），**地图坐标不动**——模型演进不破坏
   导航数据。阶段 4 全部 Nav2 配置的 `robot_base_frame: base_footprint`
   依赖这个决定。

### 1.3 轮子与三点支撑：能落地才能跑

```xml
<joint name="left_wheel_joint" type="continuous">   <!-- 可无限旋转 -->
  <origin xyz="-0.12 0.14 ${wheel_center_z}"/>      <!-- 车尾两侧 -->
  <axis xyz="0 1 0"/>                               <!-- 绕 Y 轴 = 前进方向自转 -->
  <dynamics damping="1.0" friction="1.0"/>
```

高度账（三处咬合，自己验一遍）：

```text
base_z           = wheel_radius + base_height/2 = 0.05 + 0.05 = 0.10   # 车身中心离地
wheel_center_z   = -(base_height/2) = -0.05                            # 相对 base_link
轮心绝对高度      = 0.10 - 0.05 = 0.05 = wheel_radius ✓ 轮子刚好触地

caster origin z  = -(base_z - caster_radius) = -(0.10-0.03) = -0.07
球底绝对高度      = 0.10 - 0.07 - 0.03 = 0 ✓ 万向轮也刚好触地
```

布局是**后驱三轮**：两个驱动轮在车尾（x=−0.12）+ 车头万向轮（x=+0.14）
组成三点支撑——三点共面天然稳定，这是阶段 3.2 机器人能在 Gazebo 里
"落地不翻"的几何基础。万向轮用**球体 + 低摩擦**（第 2 课 mu=0.1）模拟
"随意转向"，不引入真实的转向关节，简单且够用。

`wheel_separation: 0.28` 别小看——它不只是轮距，第 2 课会看到它被喂进
diff_drive 插件，**直接决定里程计的角速度换算对不对**。

## 第 2 课：Gazebo 扩展——摩擦、驱动、里程计、真值

### 2.1 `<gazebo reference>`：物理性格逐件设定

```xml
<gazebo reference="left_wheel_link">
  <mu1>1.0</mu1>  <mu2>1.0</mu2>     <!-- 轮胎：高摩擦 = 抓地 -->
  <kp>1000000.0</kp> <kd>100.0</kd>  <!-- 接触刚度/阻尼 -->
  <minDepth>0.001</minDepth>          <!-- 允许 1mm 压深，防抖 -->
```

摩擦分工读一遍就懂设计意图：**轮胎 mu=1.0 抓地、万向轮 mu=0.1 滑顺、
车身 mu=0.2**（万一蹭地也不拖死）。轮关节另加
`implicit_spring_damper`（ODE 隐式弹簧阻尼）——注释原话"静止时减少落地
后自己往前溜"。**仿真里的每个"物理性格"都是显式设定的，不是默认巧合。**

### 2.2 diff_drive 插件：cmd_vel 变轮速，轮速变里程计

```xml
<plugin name="diff_drive" filename="libgazebo_ros_diff_drive.so">
  <ros><remapping>cmd_vel:=cmd_vel_gazebo</remapping></ros>
  <wheel_separation>${wheel_separation}</wheel_separation>   <!-- 0.28 -->
  <wheel_diameter>${2 * wheel_radius}</wheel_diameter>       <!-- 0.10 -->
  <robot_base_frame>base_footprint</robot_base_frame>
  <publish_odom>true</publish_odom>
  <publish_odom_tf>true</publish_odom_tf>
</plugin>
```

它干两件事，各对应差速运动学的一半：

**① 收速度 → 驱轮子**：接收 Twist（linear.x + angular.z），按差速公式
拆成左右轮目标角速度。**② 读轮子 → 造里程计**：反向积分出 `/odom` 和
odom→base_footprint TF。换算就靠两个参数：

```text
v = (v_right + v_left) / 2          # 平均 → 线速度（用 wheel_diameter）
ω = (v_right − v_left) / separation # 差 → 角速度（用 wheel_separation）
```

**参数喂错的后果链**（面试好题）：`wheel_separation` 实车 0.30、模型填
0.28 → 车实际转 90°，里程计以为转了 84° → AMCL 的运动模型先验全错 →
激光修正负担加重。**里程计的精度上限在机械参数填对的那一刻就决定了**，
T3 能测出 scale=1.0000 正是因为模型和仿真用的是同一组数。

**remap 的伏笔**：插件只认 `/cmd_vel_gazebo`——真正的 `/cmd_vel` 留给
`cmd_vel_timeout` 中继（阶段 3.3，0.5 s 超时自动刹车；阶段 4 Nav2 的
指令就是经它进的 Gazebo）。**接口分层：插件层认"裸指令"，中继层管安全**。

配套插件 `gazebo_ros_joint_state_publisher`（50 Hz 读真实轮转角 →
`/joint_states`）替代外部 joint_state_publisher 节点，喂饱
`robot_state_publisher`，TF 树才完整——**插件替代节点，少一个进程**。

### 2.3 p3d 真值插件：给整个项目一把"验收尺子"

```xml
<plugin name="ground_truth" filename="libgazebo_ros_p3d.so">
  <ros><remapping>odom:=ground_truth</remapping></ros>
  <body_name>base_footprint</body_name>
  <update_rate>20</update_rate>
  <gaussian_noise>0.0</gaussian_noise>   <!-- 零噪声 = 物理引擎的绝对真值 -->
</plugin>
```

直读物理引擎的位姿、零噪声、20 Hz——**仿真特权**：真机没有这个话题。
它造就了 T3（22 m 误差 <1 mm 的 odom 基线）、4.4 的 AMCL 自动验收、
4.5 的三指标 gate 脚本、4.5b 的 patrol_diag 录证。**"必须有真值才能做
自动验收"这个设计，从 3.3 就埋好了。**

## 第 3 课：激光——ray 传感器与"自车红点"攻坚战

### 3.1 扫描面离地 0.22 m：三个属性拼出来的

```text
laser_link 安装高（相对 base_link）= base_height/2 + laser_height/2 = 0.05+0.02 = 0.07
base_link 离地                     = base_z                        = 0.10
传感器 pose（相对 laser_link）      = laser_height/2 + laser_scan_z_offset = 0.02+0.03 = 0.05
────────────────────────────────────────────────────────────────
扫描面绝对高度                      = 0.10 + 0.07 + 0.05            = 0.22 ✓
```

场景规格"激光离地 0.22 m"不是随手填的，是**三级高度链的合成结果**——
每一级都有独立理由（贴车顶 / 光心抬高避开车身）。改任何一个属性都会
动到 0.22，**参数的"来源链"比数值本身更重要**。

### 3.2 传感器配置逐行读

```xml
<sensor name="laser" type="ray">
  <update_rate>10</update_rate>                       <!-- 10 Hz，阶段4 hz 验证过 9.99 -->
  <pose>0 0 ${laser_height/2.0 + laser_scan_z_offset} 0 0 0</pose>  <!-- 光心抬高 -->
  <horizontal>
    <samples>360</samples>  <min_angle>-π</min_angle> <max_angle>π</max_angle>
  </horizontal>                                        <!-- 360 线 × 360° ≈ 1°/线 -->
  <range><min>0.30</min> <max>12.0</max></range>
  <noise><type>gaussian</type> <stddev>0.01</stddev></noise>  <!-- 1cm 噪声，像真雷达 -->
  <plugin filename="libgazebo_ros_ray_sensor.so">
    <remapping>~/out:=scan</remapping>                 <!-- 插件默认话题 remap 成 /scan -->
    <frame_name>laser_link</frame_name>                <!-- 数据的坐标归属 -->
  </plugin>
```

`min 0.30` 的依据写在注释里：**大于雷达到车身外轮廓水平距离（约 0.25 m），
留余量**——小于它的命中在 /scan 里变 `inf`，RViz 不画。`max 12.0` 盖住
10 m 房间。**注意 min_range 出现在三个地方且必须一致**：URDF 属性、
AMCL yaml、costmap yaml——阶段 4 复习课讲过的"参数来源链对齐"。

### 3.3 自车红点：一次教科书级的三因三治

现象：RViz /scan 里车身周围一圈红点（雷达"看见"了自己）。

| 成因 | 修法（现行代码） |
|---|---|
| ① 传感器在 link 几何中心，水平射线先撞雷达外壳 collision | laser_link **不放 collision**（只有 visual） |
| ② 扫描平面离车身太近 | 光心 pose 抬到圆柱顶面再 +3 cm（`laser_scan_z_offset`） |
| ③ 近距车身角点没被滤掉 | `min_range 0.30 ≥ 车身半径 0.25` 留余量 |

注释里还有个反直觉的正常现象值得记：**远处细柱在 /scan 里"线条稀疏"
不是 bug**——r=0.15 m 柱子在 1.6 m 外张角约 11°，360 线里只有约 11 根
打中它。角分辨率（1°/线）决定"多细的东西能被几根线扫到"，这直接关联
阶段 5 的教训：**传感器能不能看见，先算张角**。

## 第 4 课：相机——光轴约定排障战（3.5 复盘）

### 4.1 配置与规格的挂钩

```xml
<sensor name="camera" type="camera">
  <update_rate>10</update_rate>
  <horizontal_fov>1.047</horizontal_fov>   <!-- 60°，规格 §2 -->
  <image><width>640</width> <height>480</height> <format>R8G8B8</format></image>
  <frame_name>camera_link</frame_name>     <!-- 阶段 5 可改 optical_frame -->
```

规格 §4 的像素密度账（阶段 5 检出率的物理基础）从这里算起：HFOV 60°、
640 px → 焦平面像素角分辨率 ≈ 640/60° ≈ 10.7 px/°；1.2 m 处水平视野宽
≈ 2·1.2·tan30° ≈ 1.39 m → **462 px/m**；8 cm 指示灯 ≈ **37 px** > 20 px
小目标下限 ✓。**相机参数一动（FOV/分辨率），巡检几何就重算**——
这就是为什么规格文档要冻结。

### 4.2 排障复盘：画面朝下 vs 朝前，差在一套约定

**现象（3.5 当时的坑）**：相机画面俯视车顶（rqt 里一片蓝），多轮调
pitch 都不对。

**根因**：两个世界的光轴约定不同——

| 约定 | 光轴 | 流行于 |
|---|---|---|
| **Gazebo Classic 11 传感器** | **+X** | 本项目引擎（血泪验证） |
| Ignition / ROS 相机文档常写 | −Z | 部分教程抄来的 |

照"−Z 约定"补 pitch=+90°（1.5708）想把光轴从"朝下"掰回"朝前"——
在 Classic 里这一转恰好把 +X 转成了 **−Z（朝地）**，雪上加霜。

**最终方案（现行代码）**，三件套互相锁死：

```text
① 布局：拆掉相机支架，前保险杠低位（x=0.215, z=0.02，光心离地 0.12 m）
② sensor <pose> 0 0 0 0 0 0 恒等   —— camera_link 与 base_link 同向，+X 天生朝车头
③ camera_joint 禁止写 rpy
```

注释里那句"joint 禁止写 rpy"是纪律：**朝向只在 sensor pose 一处表达，
joint 和 sensor 两处各转一点 = 谁也说不清合成结果**。单一事实源原则
（和阶段 2 的"一条 TF 边一个发布者"、coords.py"禁止第三次手算"同源）。

**方法论沉淀**（这张表背下来）：

```text
跨引擎/跨版本排障：先查"约定差异"，再查"参数对错"
第一手验证 > 文档转述：rqt 花几分钟实测，胜过抄十篇博客
两处表达同一旋转 → 必出灵异问题；删到只剩一处
```

### 4.3 camera_optical_frame：给阶段 5 铺的最后一颗螺丝

```xml
<joint name="camera_optical_joint" type="fixed">
  <parent link="camera_link"/>
  <child link="camera_optical_frame"/>
  <origin xyz="0 0 0" rpy="${-pi/2} 0 ${-pi/2}"/>
```

机械系（camera_link：X 前 Z 上）与**光学系**（图像：Z 前 X 右 Y 下）差一个
固定旋转。阶段 5 的检测框在像素里、阶段 6 要投成地图坐标——**像素→3D
方向必须先在光学系里做**，这条 (−90°, 0, −90°) 的静态边就是那座桥。
它在阶段 3 就躺在 URDF 里了。

## 附录 B：参考答案

**第 1 课**

1. base_link 中心离地 0.10 m：导航原点悬空，footprint/_costmap 的 z=0
   平面几何全部要加偏移；且每次改 base_height，全地图坐标跟着动。
   空 link 把"车的二维身份"和"车的身材"解耦。
2. 轮子全程转圈没有角度限位，revolute 要设上下限（limit）；axis Y 是
   "轮轴垂直于前进方向"——车头 +X，轮绕 Y 转就是前进/后退。
3. base_z = 0.06+0.05 = 0.11（车身上抬 1 cm），但 wheel_center_z 公式
   不含轮半径（仍是 −0.05）→ 轮心绝对高度 0.06 > 轮半径 0.06？等于
   0.06 = 轮半径，恰好还贴地；若轮心公式也是定值则车被"架起来"或
   "沉下去"——**这正是三处咬合的意义：改一处必须连锁推演全部**。
   caster 同理会悬空/穿地。真要改轮径，三个公式都在，全部是 ${} 引用，
   改 radius 一处其余自动跟着对——**参数化的意义就在这**。

**第 2 课**

1. 简单但短视：/cmd_vel 是"上层意图"接口（键盘、Nav2、未来 LLM 都发它），
   插件只该收"最终执行值"。中继层（cmd_vel_timeout）在中间做超时刹车、
   QoS 转换——插件 remap 出来的独立话题让**安全层可以整体替换**而不碰
   URDF（冻结文件）。接口分层 = 可替换性。
2. 车实际转 90°，odom 只算出 84°（ω 反比于 separation）→ 每次转弯里程计
   少报 → AMCL 运动模型先验系统性偏 → 激光修正负担加大 → 走廊重复段
   更容易锁错峰（4.5b 机理的前置条件恶化）。**机械常数是里程计的根**。
3. 真值要和导航原点同系：AMCL/costmap 全在 base_footprint 系上做 2D
   几何，ground_truth 报 base_link 的话每个数都带 0.10 m 的 z 和不同原点，
   对比脚本要多做一层没必要的转换。**尺子要量哪，就钉在哪。**

**第 3 课**

1. ①外壳 collision → laser_link 删除 collision 只留 visual；②扫描面贴
   车身 → sensor pose 抬到圆柱顶面再 +3 cm（laser_scan_z_offset）；
   ③近距车角没滤 → min_range 0.30 ≥ 车身半径 0.25 加余量（命中变 inf）。
2. `base_height/2 + laser_height/2`（0.07，贴车顶安装）+ `base_z`（0.10，
   车身离地）+ `laser_height/2 + laser_scan_z_offset`（0.05，光心再抬高）
   = 0.22。其中任何一级改动都改变扫描面；**AMCL yaml 和双 costmap 的
   min_range 0.30 是按这个几何定的**，改高度必须连锁重审三处配置。
3. min_range 0.10 < 车身半径 0.25 → 射线开始打到自己车（车身角点、
   轮子、caster）→ /scan 里出现贴车假障碍 → costmap 把自己周围涂成
   lethal → 机器人认为"我被包围了"，Nav2 无法起步或反复 recovery。
   **min_range 的下限由"车有多大"决定，不是"想看多近"决定。**

**第 4 课**

1. Classic 的传感器光轴沿 +X，教程按 Ignition/ROS 的 −Z 约定教"补
   pitch 90°"，一补反而把 +X 转成 −Z 朝地。三件套：拆支架改为前保险杠
   低位 + sensor pose 恒等 + joint 禁止 rpy（朝向只在 sensor pose 一处
   表达）。
2. 640 px / HFOV 60° ≈ 10.7 px/°；1.2 m 处视野宽 2×1.2×tan30° ≈ 1.39 m
   → 462 px/m → 0.08 m × 462 ≈ 37 px。改 FOV（变小像素变多）、改分辨率
   （640→1280 翻倍）、改停车距离（规格定 1.0~1.5 m 的原因）都会动它；
   闸门"小目标 ≥20 px"就是对这条链的约束。
3. camera_link 是机械系（X 前 Z 上，跟车身同向）；optical_frame 是光学系
   （Z 前 X 右 Y 下，跟图像像素行列对齐），两者差 (−90°, 0, −90°) 固定
   旋转。检测框的 (u,v) 像素坐标遵循光学系约定，要投影成 3D 方向/地图
   坐标必须先在光学系里做——阶段 6 的"检测→map_pose"第一步。
